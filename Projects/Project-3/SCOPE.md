## Stack, and why

**Backend — NestJS 12 (ESM)**

- ESM is the v12 default and unlocks the modern toolchain: **Vitest**,
  **oxlint**, **Rspack**. Requires Node 20.19+ / 22.12+.
- **The one sharp edge:** TypeORM cannot glob entities or migrations under
  ESM. Entities load via `autoLoadEntities: true` + `TypeOrmModule.forFeature`,
  and migrations go in an **explicit array** in the DataSource. Set up
  correctly on day one this never resurfaces; done lazily it burns an evening.

**Database — Neon Postgres**

- App connects on the **pooled** endpoint; migrations run against the
  **direct** endpoint (PgBouncer transaction mode breaks some DDL and
  prepared statements). Both need
  `?sslmode=require&channel_binding=require`.
- **Neon branching is a real differentiator**: a `dev` branch per developer, a
  throwaway branch per CI run so integration tests hit real Postgres, and a
  `main` branch for the graded deployment. Document this in the README — it is
  the kind of thing that reads as professional.

**Validation — two libraries, one rule each**

The split is a principle, not a compromise: **class-validator owns the HTTP
boundary, because it is what produces the OpenAPI document. Zod owns every
other trust boundary.**

*class-validator + `class-transformer`* — one DTO class per request
body/query/param, decorated with `@ApiProperty`, behind a global
`ValidationPipe({ whitelist: true, forbidNonWhitelisted: true, transform: true })`.
This is exactly the convention in `Project-2/backend/AGENTS.md`, so the house
style carries over intact — and it's the most battle-tested path in NestJS,
which keeps the docs pipeline boring and reliable.

*Zod* — every place data arrives from outside the HTTP layer, where there is
no OpenAPI document to generate and Zod's inference is simply better:

- **Environment config** — a Zod schema in `@nestjs/config`'s `validate`,
  giving a fully typed `AppConfig` and a fail-fast boot on a bad `.env`
  (this is what replaces Joi).
- **`background_task` payloads** — the column is `jsonb`, so a row read back
  is untyped by definition. Each task type declares a Zod schema and parses
  its payload before the handler runs.
- **Gemini output** — the data-quality narrative comes back as structured
  JSON and is `safeParse`d, so a malformed LLM response can never corrupt a
  `DataQualityReport` row.
- **Parsed spreadsheet shapes** — inferred column types and row records out of
  `csv-parse` / `exceljs`.
- **Frontend forms** — Zod + React Hook Form on the Next.js side.

**Docs pipeline**

```
DTO class + @ApiProperty  →  ValidationPipe            runtime validation
                          →  SwaggerModule.createDocument   OpenAPI document
                          →  @scalar/nestjs-api-reference   branded reference UI at /reference
                          →  openapi-typescript             typed frontend client
```

Because the frontend generates its types from the published OpenAPI document
rather than importing backend source, the two apps stay genuinely independent
— **the API contract is the boundary**, which is exactly what you'd want if
companies really were consuming this.

**Observability — `@nestjs/observe`**

Nest 12's other headline feature, and a better fit here than a generic Node
APM because it hooks Nest's own lifecycle — controllers, guards, interceptors,
resolvers, scheduled jobs — so telemetry arrives in framework vocabulary.

```typescript
// observe.ts
export const { ObserveModule, ObserveInstrument } = createObserveModule({
  traceIdGenerator: (req) => req.headers['x-request-id'] ?? randomUUID(),
  attachTraceIdToLogs: true,
});

// app.module.ts
ObserveModule.forRootAsync({ /* appKey, appSecret from ConfigService */ })

// main.ts
await NestFactory.create(AppModule, { instrument: ObserveInstrument });
```

Four things make this genuinely load-bearing for Gridline rather than
decorative:

- **Tenant-tagged traces.** `http.getUserId` plus a `setAttributes` that
  stamps `companyId` on every span means traces are filterable *by tenant* —
  which company is erroring, which one is burning quota. That is the exact
  question a multi-tenant SaaS operator asks, and it falls out for free.
- **The background task runner is instrumented automatically.** Observe
  covers `@nestjs/schedule` intervals, so the durable task table gets wait
  time, retries and failure grouping without a Bull Board equivalent. Choosing
  the simple job table costs no visibility.
- **Redaction, configured seriously.** Defaults already mask JWTs, AWS keys,
  PEM blocks and card numbers; add `keys: ['passwordHash', 'tokenHash',
  'appSecret']` and patterns for activation/invite tokens. This app moves
  credentials — the redaction config should look deliberate.
- **Custom business metrics**, not just infra: `gridline.files.uploaded`,
  `gridline.quota.exceeded`, `gridline.subscription.changed`,
  `gridline.billing.invoice_finalized`.

Also: `ignore: ['/health']` so healthchecks don't eat the event budget,
`serviceVersion: process.env.GIT_SHA` for the Releases view, and the Next.js
BFF forwards `x-request-id` so a single trace spans web → api.

Two honest limits to design around: **logs are a paid-plan feature** and the
free tier keeps **3 days of retention**. So `nestjs-pino` stays for structured
stdout logging, correlated by Observe's trace id via `attachTraceIdToLogs`.
And Observe is for operating the service — the in-app `/analytics/usage`
surface remains the product-level analytics. Different audiences, no overlap.

**Frontend — Next.js 16**

App Router + Turbopack, TypeScript, **Tailwind v4** (CSS-first `@theme`),
Radix primitives styled from scratch (deliberately *not* stock shadcn — it
should not read as generated), TanStack Query, Recharts for analytics.
JWT lives in an httpOnly cookie set by Next route handlers acting as a thin
BFF, reserved at `/session/*` — never `/api/*`, which is the real backend's
public path (see *Docker*, below, for why that separation is load-bearing,
not stylistic). No token ever touches browser JS.

## Developer portal — the Scalar surface

Swagger UI is never mounted. `@nestjs/swagger` stays, but purely as the
*generator* that reads the class-validator DTOs and `@ApiProperty` decorators
into an OpenAPI document — **Scalar is the renderer**. Three layers, all
in-repo and account-free:

**1. API Reference at `/reference`** — `@scalar/nestjs-api-reference` mounted
as middleware over the generated document. Open source and self-hosted, themed
with custom CSS driven by the same Gridline tokens as the dashboard. It ships
with an **embedded API client**, so every endpoint is executable from the page
with auth attached — the "try it" surface Swagger UI does badly.

```typescript
const document = SwaggerModule.createDocument(app, config);
app.use('/reference', apiReference({ content: document, customCss: gridlineTheme }));
```

**2. Guides at `/docs/*` in the Next.js site** — MDX: quickstart,
authentication, the permissions model, plans and billing. Keeping these in the
repo means they wear the brand natively and a grader needs no external
account. *(Scalar Docs — the managed portal with GitHub sync, PR previews and
a custom domain — is the alternative if Gridline ever became real, but it
moves content out of the repo, which is the wrong trade here.)*

**3. The document itself at `/openapi.json`**, plus a committed snapshot. That
one artifact feeds three consumers: the reference UI, `openapi-typescript` for
the frontend's typed client, and the **standalone Scalar API Client** (the
open-source Postman replacement) for anyone who wants to poke at Gridline
outside the browser. Scalar's SDK Generator would be the paid equivalent of
that third path; `openapi-typescript` does the job locally for free.

**Stretch, explicitly cuttable — Scalar Agent (MCP).** Upload the OpenAPI
document and Scalar exposes it as an MCP server with delegated auth, so an LLM
agent can work Gridline — list files, read data-quality reports, check quota
and billing — without ever receiving upstream credentials, and with scoped
access per installation. It is a genuinely 2026-credible SaaS feature and it
ties George's HIGGS AI track to the product. But it needs a Scalar account and
a publicly reachable API, and there are already two bonus features for a
2-point line item. **Sequence it dead last, on the deployed demo only, after
all 40 points are locked.**

  and `src/shared/{components/{layout,ui},const,hooks,lib,middleware}`.
- **Route groups** `(public)` and `(protected)`, each with its own `layout.tsx`,
  `loading.tsx` and `error.tsx` — the protected group is where the app shell

  magic strings scattered through JSX.
- Its toolchain is already what Gridline wants: Next 16, React 19, Tailwind v4

- **Diverge on two things.** Its violet primary — see the palette note above.

  as a second auth system beside it is a known complexity trap. The thin BFF
  cookie approach stays.

**From `nestjs-starter` — take the vocabulary, raise the floor.**

- `src/guards/`, `src/decorators/`, `src/enums/` as shared folders; `@User()`
  and `@Roles()` param decorators; DTOs colocated per module; the
  `passport-google-oauth2` strategy shape.
- Improve on it where it's thin: its guard writes an untyped `request.userId`
  — Gridline uses the CLS tenant context and a typed request user. Its Google
  strategy reads `process.env` directly — Gridline goes through the
  Zod-validated `ConfigService`. It has no API docs, no Swagger, no tests on
  auth — Gridline has Scalar and a real suite.

## Generated API docs — structure by script, prose by hand

The insight is right: the *shape* of the document is mechanical and should
never be typed by a human, but the *prose* is editorial and no script can
invent it. So split them.

**`npm run docs:generate`** boots the Nest app in a no-listen context, calls
`SwaggerModule.createDocument()`, and gets the full structure for free from
the class-validator DTOs and controller decorators — every path, schema,
parameter, status code and auth requirement. Then it merges a **prose
sidecar** and serialises to YAML.

```
docs/
├── openapi.yaml              generated, committed, never hand-edited
├── openapi/                  same document split per tag, for reviewable diffs
│   ├── auth.yaml
│   ├── files.yaml
│   └── …
└── descriptions/             hand-written, the only file a human touches
    ├── auth.yaml             operationId → { summary, description, examples }
    └── files.yaml
```

Keeping the prose in `docs/descriptions/*.yaml` rather than inline
`@ApiOperation({ description })` means controllers stay readable, the copy can
be edited without touching TypeScript, and the writing can be done in one
sitting with the whole API in view rather than scattered across thirty files.

Two guards make it hold:

- **`docs:generate` fails on an operation with no prose entry.** A new
  endpoint cannot ship undocumented — the build tells you which
  `operationId` is missing a description.
- **`npm run docs:check`** regenerates into a temp file and diffs against the
  committed `openapi.yaml`, failing on drift. Run it in CI; the committed
  document can then be trusted as the contract that Scalar renders and
  `openapi-typescript` consumes.

## Identity model — email is not the key

Apple is dropped. But the problem it exposed is real and general, and fixing
it properly makes the whole auth system better. The flaw was never Apple's
relay address — it was **using email as the identity key**. That breaks in
several ordinary ways:

- Someone invited at `giorgi@acme.com` signs in with `giorgi.personal@gmail.com`.
- A company changes domain and everyone's work address moves.
- Any provider that returns a relay or aliased address.

So Gridline separates **who someone is** from **how they prove it**.

### Two tables, not one

`User` holds no credentials at all. Credentials live in `auth_identity`:

| Field | Notes |
|---|---|
| `userId` | → `User` |
| `provider` | `password` \| `google` \| … |
| `providerUserId` | the provider's **stable subject** (`sub`), never the email |
| `email` | the address *as that provider reports it* — may be a relay, may differ from the work address, may be null |
| `emailVerified` | the provider's own claim |
| `lastUsedAt` | |

with `UNIQUE (provider, providerUserId)`. One user, many identities. Email
becomes an attribute rather than a primary key, and `User.email` goes back to
being what it should have been all along: **the company contact address** —
where invites and notifications are sent, set by the admin who invited them.
`AuthIdentity.email` is whatever the provider says. **They are allowed to
differ forever, and nothing breaks.**

### The invite token *is* the proof of identity

This is the move that dissolves the whole problem. When an employee is
invited, the signed single-use token is sent to their work address —
**possession of that link already proves who they are.** So the invite page's
"Continue with Google" carries the invite token through the OAuth `state`
parameter, and the callback binds whatever identity comes back to *the invited
user*, with **no email comparison at any point**.

A relay address, a personal Gmail, a completely unrelated address — all fine.
The provider's only job is to hand back a durable `sub` to recognise them by
next time. This is how Slack, Notion and Linear actually work, and it is
strictly more robust than matching strings.

### When email *is* allowed to matter

Discovery by email is the dangerous path — auto-linking on an unverified
provider email is a classic account-takeover vector, where an attacker creates
an OAuth account carrying your address at a sloppy provider and inherits your
account. So the rules are narrow:

| Situation | Rule |
|---|---|
| **Sign-in** | Look up by `(provider, providerUserId)`. **Never** by email. |
| **Auto-link to an existing user** | Only when the provider asserts `email_verified === true` *and* it exactly matches that user's verified contact address. Otherwise, refuse. |
| **Company registration** | Provider email prefills the form and, if verified, **skips the activation email**. Country and industry are still collected. |
| **Known identity, unknown email** | Irrelevant — sign them in. Email was never consulted. |
| **Unknown identity, unknown email** | Offer *register a new company*. Never silently join an existing one. |

Relay-style addresses are flagged on arrival and excluded from discovery and
from outbound mail entirely.

### The universal escape hatch

**Settings → Linked accounts.** An already-authenticated user clicks "Link
Google", and the callback binds the returned `sub` to the *current session's*
user — again with zero email matching. Every mismatch case in the table above,
relay or otherwise, has this as its answer, and it needs no admin
intervention.

And joining a company stays non-self-service by design: someone who should
belong to a tenant but has no identity and no matching email gets re-invited
by their admin, and the invite-token flow binds it. In a B2B tenant app, that
is the correct answer rather than a limitation.

### What this buys

Adding Apple later becomes genuinely trivial — one strategy implementing an
`OAuthProvider` seam that returns `{ providerUserId, email, emailVerified,
name }`. The relay problem is *structurally gone* rather than special-cased,
because nothing downstream ever compares emails. Not building Apple is a
scheduling decision now, not an architectural one.

The OAuth callback sits on the NestJS side, and Docker putting both apps on
one origin means the session cookie is same-site with no token hand-off dance.

## WebSockets — one job, done well

`@nestjs/websockets` + Socket.IO, authenticated on the handshake with the same
JWT and joined to a `company:<companyId>` room. Not decoration — it exists
because Gridline has genuinely asynchronous work the user is waiting on:

- **Live data-quality status.** Upload a file and the detail page moves
  `queued → profiling → ready` on its own, with the report rendering in place.
  This is the demo moment: the background task runner becomes visible instead
  of being an implementation detail behind a polling spinner.
- **Live quota meter.** A teammate uploads and every open dashboard in that
  company ticks. It makes the multi-tenancy tangible in a way no screenshot
  does.
- **Audit log live tail** for admins.

Room membership respects the ACL — events about a `restricted` file are
emitted only to granted users, not the whole company room. The tenant scope
guard applies to sockets exactly as it does to HTTP.

**One real gotcha, resolved:** Next.js `rewrites()` does not proxy WebSocket
upgrades reliably. `docker-compose.yml` fronts both apps with a **Caddy**
reverse proxy instead — see *Docker — one origin, five services* for the
routing table and why that also settled the backend's public `/api/*`
prefix and introduced `/session/*` for Next's own BFF handlers.

## GraphQL — a separate surface with a real reason

GraphQL does **not** replace the REST API, and Gridline does not become a
GraphQL app. It gets exactly one job, where it genuinely beats REST:

**`/graphql` is the read-only analytics surface.**

The analytics dashboard wants many differently-shaped aggregates over the same
few entities — files per day by uploader, quota burn-down across a period,
plan history joined to invoice totals, per-employee activity with variable
grouping. In REST that becomes either a dozen bespoke endpoints or one
endpoint with fifteen query parameters, and every new chart needs backend
work. That is the textbook case for GraphQL, and it's honest justification
rather than résumé-driven design.

Deliberate constraints keep it from metastasising:

- **Read-only.** No mutations. Every write stays REST, so there is exactly one
  path that changes state and one place permissions are enforced for writes.
- **Analytics schema only** — it never exposes auth, billing writes, or file
  contents.
- Tenant-scoped through the **same CLS context**, so a resolver cannot see
  another company's rows even if the query asks.
- **Depth and complexity limits** plus a cost guard, because an open query
  language against an analytics database is otherwise a denial-of-service
  surface.
- Code-first schema; args validated by class-validator through the same global
  pipe as REST.

Bonus: `@nestjs/observe` instruments GraphQL resolvers (it requires
`@nestjs/graphql` 13.4.4+), so the resolvers land in the same traces as
everything else with no extra wiring.

## Reliability without event-driven architecture

George is deliberately stepping off the outbox/CQRS pattern from Project-2.
Reliability comes from cheaper, more legible primitives instead:

1. **Transactions.** Every multi-row state change (register company + admin +
   token; change plan + close period + write proration) runs in one
   `dataSource.transaction`.
2. **A durable task table — not an event bus.** `background_task`
   (`type`, `payload`, `attempts`, `run_after`, `status`, `last_error`),
   claimed with `SELECT … FOR UPDATE SKIP LOCKED`, drained by a
   `@nestjs/schedule` interval, exponential backoff, dead-letter after N
   attempts. It exists for exactly two jobs: **send email** and **build data
   quality report**. ~150 lines, no Redis, no broker, survives a restart.
   Say plainly in the README that this is a job queue, not an event backbone —
   the restraint is the point.
3. **Optimistic locking.** `@VersionColumn` on `Subscription` so two
   concurrent plan changes cannot interleave.
4. **Idempotency keys** on upload and plan-change, so a retried request
   cannot double-charge or double-count quota.
5. **Observability.** `@nestjs/observe` for traces, errors, runtime metrics
   and job telemetry (detailed above); `nestjs-pino` for structured stdout
   logs carrying Observe's trace id (redaction and correlation detail in
   *Request pipeline & data access*, below); `nestjs-cls` for the tenant
   context; `/health` via `@nestjs/terminus`; graceful shutdown (new in Nest
   12 for the Express adapter).
6. **Tests that matter.** Vitest unit tests over the billing calculator with
   injected fixed clocks; integration tests against a per-run Neon branch.

## Request pipeline & data access

Cross-cutting building blocks every module reuses rather than reimplements —
built once in Milestone 1, consumed by `employees/`, `files/`, `billing/`,
and the bonus audit/analytics surfaces.

### Custom decorators

- **`@CurrentUser()`** — param decorator reading the resolved
  `{ id, companyId, role }` off the request, populated identically whether
  `JwtAuthGuard` or `ApiKeyGuard` authenticated the call. Replaces the
  untyped `request.userId` in `Datodia/nestjs-starter`'s guard with a shape
  the compiler checks.
- **`@Public()`** — a metadata flag read by a global auth guard. Auth on
  Gridline is **opt-out, not opt-in**: every route requires a valid identity
  and an active subscription unless explicitly marked `@Public()`
  (registration, login, activation, refresh, accept-invite, the OAuth
  callback, `/health`). A new route is secure by default — there's no guard
  to forget to add.
- **`@Roles(...)`** — already load-bearing for RBAC (see *Tenancy + RBAC*).
- **`@RequireScopes(...)`** — the API-key analogue of `@Roles`, read by
  `ApiKeyGuard` and composable with it, so a route can demand a role **and**
  a scope.
- **`@IdempotencyKey()`** — pulls the `Idempotency-Key` header, paired with a
  pipe that validates it's a UUID. This is the concrete mechanism behind the
  "idempotency keys" primitive named above: `POST /files` and
  `PATCH /subscriptions/me` store `(idempotencyKey, responseSnapshot)` and
  replay the snapshot on a retry instead of re-running the side effect.
- **`@ApiPaginatedResponse(Dto)`** — a composed Swagger decorator
  (`applyDecorators` wrapping `@ApiOkResponse` + `@ApiExtraModels`) so every
  list route's OpenAPI schema shows the real `{ data, meta }` envelope
  instead of a bare array, feeding straight into the generated-docs pipeline.

### Custom pipes

Two, each solving something the built-ins genuinely can't:

- **A magic-byte `FileValidator`**, plugged into Nest's own
  `ParseFilePipeBuilder`
  (`@UploadedFile(new ParseFilePipeBuilder().addValidator(new MagicByteValidator()).build())`).
  Nest ships a built-in `FileTypeValidator`, but it checks the *reported*
  MIME type — trivially defeated by renaming a `.exe` to `.csv`, exactly the
  attack the brief's "CSV, XLS, XLSX only" requirement has to survive.
  `MagicByteValidator` reads the first bytes via `file-type` instead of
  trusting `Content-Type`. This is where that check has always belonged: a
  pipe validates an argument before the handler runs, and the uploaded file
  *is* an argument.
- **`ParseSortPipe`** — turns a raw `?sort=-createdAt,fileName` query string
  into a typed `{ field, direction }[]`, validated against a per-route
  whitelist supplied via a `@SortableFields([...])` decorator. This can't be
  a static DTO decorator because the whitelist differs per resource; it has
  to read route metadata, which is exactly what a `PipeTransform` is for.
  The whitelist is never wider than the indexed columns below — sorting on
  an unindexed column is a correctness bug waiting to become a performance
  bug.

### Structured logging — Pino

`nestjs-pino` via `LoggerModule.forRootAsync`, with Nest's own bootstrap
logger bridged into it (`bufferLogs: true` + `app.useLogger(app.get(Logger))`)
so there's one log stream, not two loggers racing on stdout.

- **JSON in production, `pino-pretty` in dev** — gated on `NODE_ENV`, so local
  output stays readable while the graded/deployed instance emits structured
  lines a log platform can parse.
- **Correlated, not just timestamped.** `nestjs-cls`'s tenant context feeds a
  `customProps` hook that stamps every line with `{ companyId, userId,
  traceId }` — the same `traceId` Observe's `attachTraceIdToLogs` carries —
  so a bad log line and its full trace are one click apart in either
  direction.
- **Redaction, the same discipline as Observe's.** Pino's own `redact` config
  masks `req.headers.authorization`, `req.headers.cookie`, and any
  `*.password`/`*.passwordHash`/`*.tokenHash` path — the local-stream half of
  the policy already specified for Observe; the two are easy to specify once
  and forget to mirror.
- **Levels with a default that can't leak.** `error`/`warn` always logged;
  `info` on state-changing requests; `debug` (which would include request
  bodies) is opt-in via `LOG_LEVEL=debug` and never the graded default.

### Pagination, sorting & filtering

One contract, applied by growth pattern rather than uniformly:

| Shape | Used by | Why |
|---|---|---|
| **Offset** (`page`, `limit` → `{ data, meta: { page, limit, total, totalPages } }`) | `GET /employees`, `GET /billing/invoices`, `GET /api-keys` | Small, bounded lists — a plan caps seats at 11, one invoice lands a month — where a dashboard wants real page numbers. |
| **Cursor / keyset** (`cursor`, `limit` → `{ data, meta: { nextCursor, hasMore } }`) | `GET /files`, `GET /audit` | Append-only, potentially large, time-ordered. Keyset avoids the `OFFSET 50000` cliff — Postgres still scans and discards every skipped row — which a year of Premium uploads will eventually hit. |

The cursor is an opaque, base64-encoded `(createdAt, id)` pair, never
`createdAt` alone — two rows landing in the same millisecond would otherwise
break the page boundary. That tie-break is the easy detail to forget, and the
reason keyset pagination has a worse reputation than it deserves.

**Sorting** goes through `ParseSortPipe` against a whitelist never wider than
the indexed columns below — `?sort=-createdAt` on `files` is fine,
`?sort=summaryText` is a 400, not a slow query.

**Filtering** is one typed DTO per resource
(`FilesFilterDto { mimeType?, visibility?, uploaderId?, uploadedAfter?,
uploadedBefore? }`), validated by the existing global `ValidationPipe` and
translated into conditional `QueryBuilder.andWhere()` calls — never
string-concatenated SQL. On `files/`, the visibility predicate (stated once,
above) always runs *first*; a filter can narrow what a caller sees, never
widen it.

### Aggregation, projection & indexing

The Postgres/TypeORM shape of the same three concerns Mongo's aggregation
pipeline is usually reached for:

- **Aggregation** — TypeORM `QueryBuilder` with `.select()`/`.addSelect()`
  holding `COUNT`/`SUM`/`AVG` plus `.groupBy()`/`.having()`. Exactly two
  places need it: `billing.calculator.ts`'s per-period seat and usage
  rollups, and `GET /analytics/usage` (files/day, per-employee activity,
  quota burn-down) — the read-only GraphQL resolvers described above are a
  second surface over these same aggregate queries, not a separate
  implementation of them.
- **Projection** — selecting only the columns a response needs, via
  `QueryBuilder.select([...])` or `class-transformer`'s
  `@Expose()`/`@Exclude()` groups on the response DTO.
  `GET /companies/me/members` (`{ id, fullName }` and nothing else) is
  already a projection in this plan, not a new idea — the same discipline
  extends to `files/` list rows (no `storageKey` needed for a table) and
  `GET /audit` (`metadata` jsonb loads only on the single-entry read, never
  the list).
- **Indexing** — the concrete migration checklist, because "index
  everything" isn't a strategy:
  - Every tenant-scoped table gets a composite index **leading with
    `companyId`**, since `TenantScope` puts that predicate in every query
    without exception. `idx_file_asset_company` on
    `(companyId, deletedAt, createdAt)` doubles as `GET /files`'s
    keyset-pagination index.
  - `idx_audit_log_company_created` on `(companyId, createdAt DESC, id)` —
    the keyset index for `GET /audit`.
  - Unique composites: `(provider, providerUserId)` on `AuthIdentity`,
    `(companyId, email)` on `User`, `(fileId, userId)` on `FileAccessGrant`.
  - `idx_usage_event_company_period` on `(companyId, periodKey)` — the hot
    path for both the per-upload quota check and the billing rollup job.
  - Unique `(tokenHash)` on `RefreshToken` for O(1) lookup on every refresh.
  - A **partial index** —
    `CREATE INDEX ON file_asset (companyId, createdAt) WHERE deleted_at IS NULL`
    — since soft-deleted rows are never read on the hot path but do
    accumulate forever, this keeps the common-case index from growing with
    dead rows. Worth naming explicitly; it's the one technique here that
    isn't obvious from the ORM alone.
  - **Deliberately not indexed:** `Invoice.lineItems` and
    `BackgroundTask.payload` — opaque `jsonb` read only by primary key, never
    queried into. A GIN index there would be pure write cost for zero read
    benefit. The negative case matters as much as the positive list.

## Domain model (TypeORM entities)

`src/core/` holds cross-cutting infra — tenant context, tasks, mail, storage,
ai, config. Every other top-level folder is a domain module owning its
entities, DTOs, service, controller. All `status` / `type` / `industry`
columns below are Postgres enums, created and altered only through
migrations. Indexing strategy for these tables is specified once, in
*Request pipeline & data access* above, rather than repeated per entity.

## Modules & routes (with points)

**`auth/` + `companies/` — 6 + 4 + 2 pts**
`POST /auth/register-company` · `GET /auth/activate` ·
`POST /auth/resend-activation` (rate-limited) · `POST /auth/login` ·
`POST /auth/refresh` · `POST /auth/logout` · `POST /auth/password/forgot` ·
`POST /auth/password/reset` · `PATCH /auth/password` (authenticated) ·
`GET /auth/me` · `PATCH /companies/me` (admin — name, country, industry,
billingEmail). A thin **`users/`** module owns `PATCH /users/me`, the person's
own `fullName` — this is the *personal-data* half of the brief's "change
password and personal data", which the original SCOPE only covered for the
company.

`RegisterCompanyDto { companyName, email, password, country, industry }` —
exactly the brief's five fields. One transaction creates the `Company`
(`pending_activation`, `billingEmail = email`), the admin `User` (`invited`),
its `AuthIdentity(password)`, and the activation `AuthToken`; then an email
task is queued.

Login is refused unless the company is `active` **and** the user is `active`.

**Token TTLs:** access **15 m** · refresh **30 d** (rotated per use, family
revoked on replay) · activation **24 h** · invite **7 d** · password-reset
**1 h**. Every expiry path has a resend/restart route so a stale link is never
a dead end.

**`tenancy/` + RBAC — 3 pts**
`JwtAuthGuard` populates CLS `{ userId, companyId, role }`; `RolesGuard` +
`@Roles('admin')`; a `TenantScope` helper so every tenant query is
`companyId`-bound at one choke point rather than ad hoc `where` clauses. A
`RequireActiveSubscriptionGuard` on `files/` and `employees/` returns **402**
(pointing at plan selection) whenever the company has no live `Subscription`
— the brief's *"after logging in, the company must select a plan"*, enforced
rather than assumed.

**`employees/` — 5 pts**

*Management — admin only, 403 for employees:* `POST /employees` (creates an
`invited` user + invite token; rejects at the seat cap — an `invited` user
already holds a seat) · `GET /employees` (full records, offset-paginated) ·
`POST /employees/:id/resend-invite` (rate-limited) · `DELETE /employees/:id`
(**soft-disable** — see *Decisions*) · `POST /employees/:id/reactivate`.

*Identity — any active user:* `GET /companies/me/members` returns
`{ id, fullName }[]` and **nothing else** — no email, role, status, or
management verbs. It exists so an employee can name grantees when uploading a
restricted file, which the brief requires (req. 9) while also forbidding the
management list (req. 7). Disabled users are excluded.

*Invite acceptance (public):* `POST /auth/accept-invite { token, password }`,
or the Google flow that carries the token in `state` — see the identity
model. Sets the user `active`; billing for that seat starts now, not at
invite.

**`subscriptions/` — 5 pts**
`GET /subscriptions/me` (plan, limits, current usage, seat count, period
window, next due date) · `POST /subscriptions/me` (the mandatory first choice
after activation) · `PATCH /subscriptions/me` (upgrade/downgrade).

A plan change **closes the current period immediately**, writes a prorated
line for the outgoing plan up to the switch instant, and **opens a fresh
period anchored to the switch date** — the reading that a plan change *is* a
new subscription activation (see *Decisions*). Downgrading below the target
plan's seat cap or the period's file count so far is rejected with the numbers
that need to come down first.

Enforcement hooks: seat cap checked at invite, file quota checked at upload
(both read `PLAN_CATALOG`).

**`files/` — 4 + 3 + 2 pts**

`POST /files` (multipart). Accepts **only** `text/csv`,
`application/vnd.ms-excel` (`.xls`),
`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet` (`.xlsx`),
**verified by magic bytes** (`file-type`), never by the sent extension or
`Content-Type`. Max **25 MB**. Body carries `visibility` (`company` — default,
or `restricted`) and, when restricted, `grantedUserIds: string[]`. Stored via
`StorageService` — **`s3` driver is the default and graded path**
(`@aws-sdk/client-s3`); `local` disk is an explicit offline-dev convenience
only. On a *successful* store: one `UsageEvent`, a queued data-quality task,
an audit entry. A rejected type, a failed magic-byte check, or a storage error
consumes **no** quota.

**Quota exhausted:** Free/Basic → **402** naming the plan, the current count,
the cap and the reset date; the upload never starts. Premium → accepted, a
`$0.50` overage accrues, and the response carries an `X-Gridline-Quota-Warning`
header. The frontend shows the ceiling *before* a Free/Basic user picks a file.

`GET /files` (cursor-paginated, sortable, filterable — see *Request pipeline
& data access*) · `GET /files/:id` ·
`GET /files/:id/download` (presigned S3 URL) · `PATCH /files/:id` (change
`visibility` / grants — uploader or admin) · `DELETE /files/:id` (soft
delete: set `deletedAt`, remove the stored object, keep the row).

**The visibility predicate** (worth 3 pts — stated once, implemented once in
`TenantScope`):

```
companyId = ctx.companyId
AND deletedAt IS NULL
AND ( ctx.role = 'admin'
   OR visibility = 'company'
   OR uploaderId = ctx.userId
   OR EXISTS (SELECT 1 FROM file_access_grant g
              WHERE g.fileId = file.id AND g.userId = ctx.userId) )
```

A `restricted` file a user cannot see returns **404**, never 403 — its
existence is not disclosed.

**`billing/` — 4 pts**
Period = `billingAnchorDay → billingAnchorDay`, clamped for short months
(anchor 31 → the 28th–30th). A daily scheduled job (also
`npm run billing:run-cycle`) finalizes the closing `Invoice` and opens the
next. `GET /billing/current` (running total + line-item breakdown + seat count
+ due date) · `GET /billing/invoices` (offset-paginated) ·
`GET /billing/invoices/:id`. All three
are **admin-only**; a `suspended` company keeps read access to these and
nothing else.

Line items:
- **free** → none.
- **basic** → for each employee, `$5 × (active days in period / days in
  period)`. Only `status = active` days count — an `invited` user holds a
  seat but bills `$0` until they accept. A mid-cycle join or a soft-disable
  simply shortens that employee's interval.
- **premium** → `$300 + max(0, filesThisPeriod − 1000) × $0.50`.

The math is pure functions in `billing.calculator.ts`, taking **seat
*intervals*** (not a count) and a fixed clock — the most heavily tested file
in the repo (see *Decisions* for why intervals).

**Bonus — 2 pts (both built)**
- **AI data-quality reports.** A background task parses the file
  (`csv-parse` / `exceljs`), computes deterministic metrics — row and column
  counts, per-column null %, inferred type + inconsistency flags, duplicate
  rows, numeric min/max/mean — then asks Gemini (`@google/genai`, model from
  env) for a plain-language summary and recommendations. With
  `AI_PROVIDER=off` the metrics still render; only the narrative is skipped.
  `GET /files/:id/report`.
- **Usage analytics + audit log.** `GET /audit` (admin, cursor-paginated,
  filterable) and `GET /analytics/usage` (admin, aggregated via
  `QueryBuilder` — see *Request pipeline & data access*) — files/day across
  the period, per-employee activity, storage used, quota burn-down, plan
  history.

**`api-keys/` — beyond scope** (admin **and** employee)
`POST /api-keys` (returns the plaintext `gl_live_…` exactly once, then only
its `prefix`) · `GET /api-keys` (offset-paginated) ·
`DELETE /api-keys/:id` (revoke).

`ApiKeyGuard` accepts `Authorization: Bearer gl_live_…`, looks the key up by
hash, checks `revokedAt`, bumps `lastUsedAt`, and populates the **same CLS
context** as `JwtAuthGuard` — `{ userId: createdByUserId, companyId, role }`,
with `role` and the user's `status` re-read from the DB every request, never
frozen into the key.

**A key is act-as-user, capped by the creator's live permissions:**
- Effective permission = *(creator's current role + ACL grants)* ∩ *(key
  `scopes`)*. Scopes (`files:read`, `files:write`, `billing:read`) only ever
  **narrow**. `billing:read` is not selectable by an employee — you cannot
  grant what you do not have.
- A key can **never** mint or manage keys, and never touches auth/identity
  routes — those are session-only regardless of role, so a leaked key cannot
  establish persistence.
- An employee-created key therefore reaches exactly the employee's dashboard
  surface: upload (recorded as that user), read/list/download/preview/report
  for files that user can see, `PATCH`/`DELETE` on their own uploads,
  `GET /subscriptions/me`. Nothing under `/billing`, `/employees`, `/audit`,
  `/analytics`, `/graphql`.
- Demote or soft-disable the creator and every key they made loses the
  matching access on its next request — no revocation sweep.
- Admins list and revoke **all** company keys; employees list and revoke
  **only their own**.

These are personal keys tied to a person's lifecycle, **not** company service
accounts that survive turnover — that is a named future addition, not scope.

**`files/:id/preview` — beyond scope**
First ~50 parsed rows plus inferred column types, behind the same ACL as
download.

## Decisions on an ambiguous brief

The brief is under-specified in six places and self-contradictory in one.
Each was resolved deliberately; the rejected alternative is written down so
that if the instructor reads it differently, the reasoning — not just the
outcome — is on record.

**D1 — req. 7 vs req. 9 (the contradiction).** "An employee cannot see the
list of other employees" directly conflicts with "when uploading, choose which
employees may view the file." *Chosen:* two distinct surfaces —
`GET /employees` (admin, full records) stays 403 for employees;
`GET /companies/me/members` returns `{id, fullName}` only, for any active user,
existing solely to address a share. *Rejected:* making restricted uploads
admin-only (kills a 3-point flow for the people the requirement is about) and
returning the full employee list to everyone (violates req. 7 outright).

**D2 — "Free: 1 user" vs "Basic: 0 to 10 users."** The two tiers count
differently: a company always has ≥1 person, so Free's "1" is the admin;
Basic's "0" is zero *employees*. *Chosen:* `seats = admin + employees`
everywhere; Basic is admin + 0–10 employees, billed `$5` per employee (max
`$50`). *Rejected:* "10 total including admin" (max `$45`) — kept as a
one-line `PLAN_CATALOG` switch and named in the README.

**D3 — mid-cycle seat churn.** The brief bills "per added employee" but never
says what a mid-month add-then-remove costs. *Chosen:* per-employee
day-proration — each employee bills for their `active` days in the period.
*Rejected:* peak-concurrent-seats (a one-day hire costs a full month) and
count-at-close (invite ten, remove before close, pay nothing — gameable).

**D4 — invited-but-not-activated users.** *Chosen:* they occupy a seat (cap
enforced at invite, so no over-inviting) but bill `$0` until `active`.
*Rejected:* not holding a seat (lets a company queue 50 invites on a 10-seat
plan).

**D5 — "processing" vs "upload."** The brief says "N files processing per
month." *Chosen:* one successful upload = one unit, counted at upload. A
rejected type, a failed magic-byte check or a storage error costs nothing.
*Rejected:* counting the data-quality job as the "processing" unit — would
make quota depend on an async task and a possibly-absent AI provider.

**D6 — billing anchor after a plan change.** The brief: payment falls on "the
date the specific subscription was activated." *Chosen:* a plan change *is* a
new activation, so it re-anchors to the switch date (with immediate proration
of the old plan). *Rejected:* the original activation date anchors forever —
defensible, but makes upgrade/downgrade proration far harder to reason about
and to test.

**D7 — "delete" an employee.** *Chosen:* soft-disable — `status = disabled`,
identities/refresh tokens/API keys revoked, grants removed, seat freed and
proration stopped that day, excluded from member lists; **their uploaded files
stay with the company**. *Rejected:* hard delete — either orphans
`FileAsset.uploaderId` / `AuditLogEntry.actorUserId` or cascades away history
the company needs, and cascading breaks the audit log's immutability claim.

## Design system — Gridline

**How it gets built:** the design language is established through the
`impeccable` skill, not improvised. Milestone 2 runs `impeccable init` to write
`PRODUCT.md` (who Gridline is for, the real usage scene, the voice), then
`impeccable` new-work to commit a visual world and write `DESIGN.md` +
tokens + the component set. The two surfaces have different modes and must be
designed as such: the marketing page is **Persuade**, the dashboard is
**Operate**, the MDX guides are **Read**. The `dataviz` skill owns the chart
palette so the analytics screens and the UI read as one system.

What follows is the starting direction that work begins from, not a
substitute for it.

**Color.** OKLCH so ramps stay perceptually even.

A three-hue system — azure leads, teal carries the data, ochre interrupts.

- **Primary — deep azure (hue ≈ 248).** Actions, focus rings, active nav rail.
  Kept *deep and saturated* (around `oklch(0.52 0.19 248)`) rather than a pale
  corporate blue — precision comes from restraint in how much colour appears,
  not from draining it out. *Deliberately not violet:*
  `Datodia/nextjs-starter` ships `oklch(0.555 0.243 271)`, so every project
  built on that starter will be indigo. Gridline is not one of them.
- **Secondary — teal (hue ≈ 200).** This is what keeps the system reading
  data-native rather than bank-website: teal carries secondary chart series,
  the "processing" state on a file being profiled, and sparklines. Azure
  commands, teal measures.
- **Accent — ochre (hue ≈ 75).** Near-complementary, used *only* semantically
  and never decoratively — the filled cell in the logo, quota meters, billing
  emphasis. The "pay attention" state that is not yet an error. Disciplined
  colour assignment is most of what makes a UI read as precise.
- **Neutrals — tinted, never gray.** Hue 248 at very low chroma (0.008–0.02),
  so every surface, border and text colour sits in-family with the primary and
  nothing in the UI is `#000` or `#fff`. This reads engineered rather than
  default, and it is what keeps the whole thing off black-and-white.
- **Semantic** — emerald (within quota), amber (approaching limit), rose (over
  limit / destructive), sky (informational).
- **Data viz** — the categorical ramp runs azure → teal → ochre and outward,
  which is coherent with the UI *and* safe for the common colour-vision
  deficiencies, since blue/teal/orange stay separable. Plus a sequential ramp
  for the usage heat calendar.
- Full light and dark palettes; dark is first-class, not an inversion.

Two things outside the palette do more for "precise" than hue ever will:
**mono, tabular numerals everywhere a figure appears**, and **hairline rules
instead of shadows**. Those are load-bearing, not decoration.

**Type.** A grotesk for UI with **tabular figures everywhere numbers align** —
money, quotas, file sizes, row counts — and a mono face for IDs, storage keys
and API examples. A display face for the marketing headline only, so the
Persuade surface has a voice the dashboard doesn't need. Dense tables are a
feature of this product, not a compromise, so the scale stays compact.

**Also in the system:** an 8px spacing rhythm, hairline `1px` borders doing the
work shadows usually do, a two-level elevation scale, focus-visible rings on
every interactive element, and restrained motion (150–200ms, only where it
explains a state change).

## Docker — one origin, five services

**Built and validated** (`docker compose config` parses clean in both
profiles) as of this section's last edit — `docker-compose.yml`,
`backend/Dockerfile`, `frontend/Dockerfile`, `proxy/Caddyfile`. This
resolves the WebSocket-proxying risk this section used to just flag, and
settles two things that were previously implicit: the backend is reachable
publicly under `/api/*` even though its own routes are unprefixed, and
Next's cookie-setting BFF handlers live under `/session/*` — not `/api/*` —
so they don't collide with the real API path.

**Five services, one published port:**

| Service | Role |
|---|---|
| `db` | Local Postgres — **only with `--profile dev`** (see below) |
| `migrate` | One-shot: runs `npm run migration:run` against `DIRECT_URL`, then exits. `api` waits on it succeeding. |
| `api` | The NestJS runtime image, internal-only (`expose`, not `ports`) |
| `web` | The Next.js standalone runtime image, internal-only |
| `proxy` | **Caddy — the only service with a published port (`3000:3000`)** |

```bash
docker compose up                # Neon — DATABASE_URL/DIRECT_URL from backend/.env
docker compose --profile dev up  # + a local Postgres container instead
```

`db` carries `profiles: ["dev"]`; nothing else does, so it never starts
unless asked for. `migrate` and `api` depend on it with
`required: false`, so the dependency is silently skipped rather than erroring
when the dev profile isn't active — the same compose file serves both the
graded Neon path and local development without a `.env` change on
`migrate`/`api` themselves, only on what `DATABASE_URL`/`DIRECT_URL` resolve
to.

**Why Caddy, not Next's `rewrites()`, fronts the origin.** `rewrites()`
still exists and still proxies `/api/*` for the no-Docker local-dev case
(`npm run dev` against a locally running `npm run start:dev` API), but it
cannot proxy a WebSocket upgrade at all — the risk this section previously
named as unresolved. Caddy's `reverse_proxy` forwards the `Upgrade`/
`Connection` headers with **zero extra configuration**, which is the whole
reason it's Caddy and not nginx (nginx needs that spelled out by hand). So
in Docker, Caddy is the single public origin and routes by path
(`proxy/Caddyfile`):

| Public path | Routes to | Note |
|---|---|---|
| `/session/*` | `web` | Next's BFF — see below |
| `/socket.io/*` | `api` | WebSocket upgrade, proxied transparently |
| `/api/*` | `api` | **`handle_path`** strips `/api` before forwarding — the backend's own routes stay unprefixed exactly as written throughout *Modules & routes*; no backend change needed |
| `/reference*`, `/graphql` | `api` | Already match the backend's real, unprefixed mount points |
| everything else | `web` | Pages, the `/docs/*` MDX guides, static assets |

**The `/session/*` namespace is new, and necessary.** The "thin BFF" already
named in *Stack, and why* — Next route handlers turning the API's JWT into
an httpOnly cookie — has to live somewhere the browser can reach *without*
being forwarded straight to the real API. Since the real API is public at
`/api/*`, Next's own handlers can't also live there — Caddy would send every
request matching that prefix to `api:4000` before Next ever saw it,
`handle_path` making no exception for a path Next happens to also define.
`/session/*` (`POST /session/login`, `/session/refresh`, `/session/logout`)
is reserved for Next alone; the backend never registers anything under it.

**Two dependencies not built yet, and expected to fail until they are:**
`migrate` needs a `migration:run` script (lands with TypeORM in this
milestone); `api`'s healthcheck needs `GET /health` (lands with
`@nestjs/terminus`, also this milestone). Until then, `docker compose up`
correctly fails at the `migrate` step — that's the Docker layer being ahead
of the code that will satisfy it, not a bug in it.

## Beyond the assignment — committed

The "extra feature" line is worth 2 points and is already covered twice over
by the AI reports and the audit log. Everything here is portfolio value rather
than marks, and all four are **in scope**.

**`api-keys/` — personal API keys.** Any active user (admin **or** employee)
mints a key (`gl_live_…`, shown once, stored hashed) so files can be uploaded
programmatically. The highest-leverage addition of the four: it is what makes
a B2B data platform real, it makes the Scalar try-it panel genuinely usable
against a live account, and it is the prerequisite for the MCP stretch. A key
is **act-as-user** — it carries its creator's *live* permissions, scopes
(`files:read`, `files:write`, `billing:read`) only ever narrow, and a key can
never mint keys or touch identity. `ApiKeyGuard` populates the same CLS tenant
context as `JwtAuthGuard`, so every downstream service is unaware of which one
authenticated. Full rules in *Modules & routes → `api-keys/`*.

**Plan-tiered rate limiting.** `@nestjs/throttler` with a custom storage keyed
by `companyId`, and limits resolved from `PLAN_CATALOG` — Free throttled
considerably harder than Premium. The point is that the infrastructure limit
*is* the product limit, rather than a generic guard bolted on top. Rate-limit
headers on every response, and a 429 that names the plan and links to upgrade.

**Spreadsheet preview.** The first ~50 parsed rows rendered as a real table on
the file detail page, with inferred column types shown in the header. The
parsing already exists for the data-quality report, so this is nearly free —
and it is the whole difference between a file locker and a data product.
Respects the same ACL as the download.

**Demo mode.** A seeded company on the Basic plan with employees, files,
reports and a finalized invoice, plus a one-click "explore the demo" button on
the landing page that logs in a read-only demo admin. Graders and interviewers
who won't register otherwise never see any of the work — this is the cheapest
possible insurance against that.

**Deferred, deliberately:** branded invoice PDFs, trash + restore, weekly
usage digest emails. All reasonable, none worth displacing the billing engine.
2FA, Georgian/English i18n and outbound webhooks are out — i18n in particular
would double every piece of copy across four branded surfaces.

## Risks I'm tracking

- **TypeORM under ESM** — no globs. Entities via `autoLoadEntities`,
  migrations in an explicit array, from the first commit.
- **Nest 12 is young.** Milestone 1 proves the whole
  DTO → OpenAPI → Scalar → `openapi-typescript` chain end to end on a single
  throwaway route **before** any real feature depends on it. The one moving
  part is the `@nestjs/swagger` CLI plugin under ESM + Rspack; if it misfires,
  explicit `@ApiProperty` decorators always work and cost only verbosity.
- **Neon pooled vs direct** — migrations against the pooled endpoint fail in
  confusing ways. Two separate env vars, documented.
- **WebSockets behind one origin — resolved.** Caddy fronts the Docker
  deployment specifically because Next `rewrites()` can't proxy the upgrade;
  see *Docker — one origin, five services*. Local non-Docker dev still needs
  the Socket.IO client pointed at the API origin directly (`localhost:4000`)
  since nothing proxies WebSockets there either — a Milestone 11 detail, not
  a Docker one.
- **GraphQL scope creep** — the moment a mutation is added, there are two
  write paths and two permission models. Read-only is a hard boundary, not a
  starting point.
- **Keyset pagination needs a stable tie-break.** `createdAt` alone isn't
  unique enough under concurrent uploads; every cursor is `(createdAt, id)`,
  decided in Milestone 1's pagination kit, not improvised per route later.
- **The brief contradicts itself (req. 7 vs req. 9).** Resolved in *Decisions*
  (D1) with a members-list split. If a grader still reads it as a leak, the
  *Decisions* section is the argument — point them at it.
- **Instructor may read the seat math differently (D2).** Both readings are
  `PLAN_CATALOG` constants and both are in the README, so a challenged number
  is a one-line change, not a refactor.
- **AWS S3 is a graded requirement, not optional.** `STORAGE_DRIVER=s3` is the
  documented default; a real bucket + IAM user must exist before the file
  milestone is called done. `local` disk is dev-only and must never be the
  configuration a grader runs.
- **Observe free tier** — 300k events/month, 3-day retention, no logs. Fine
  for a demo, but the SDK must be optional: with `OBSERVE_APP_KEY` unset the
  app boots and runs normally, so a grader never needs an account. Keep
  `/health` and static assets on the ignore list.
- **Scope** — the brand and frontend surface is large. Milestones 3–9 are the
  40 graded points and come first; milestone 2 is deliberately early only
  because retrofitting a design system costs more than front-loading it. The
  cut order under time pressure is fixed in the scope reality check above:
  MCP → Docker → GraphQL → realtime → the beyond-scope four.
